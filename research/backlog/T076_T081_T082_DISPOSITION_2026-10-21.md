## T-076 — an observer outside GitHub for the dead man

**Verdict: build-complete-pending-owner-step.**

### The problem, plainly

`dead-man.yml` raises the alarm when a card is missing its pre-fight record,
but only when GitHub runs it. If GitHub throttles the schedule or turns it off
after 60 days without repository activity, the watchdog goes quiet, and quiet
looks the same as healthy.

### Options considered

| option | outside GitHub? | cost | verdict |
|---|---|---|---|
| **Supabase pg_cron + pg_net, alarm by GitHub issue** | yes | none: both ship with Supabase and are available on this project | **chosen** |
| Railway cron (`cfl-snapshotter` or a new service) | yes | `cfl-snapshotter` runs **Fridays only** (`0 18 * * 5`, D-021), so it cannot watch a 30-hour window. A new Railway service is usage-billed, which is L3 item 6 | rejected |
| A second GitHub workflow watching the first | **no**: same scheduler, same 60-day rule | none | rejected; that is what `watchdog-cadence.js` already is, and it is a mitigation |
| External uptime/heartbeat SaaS | yes | free tiers exist but it is a new vendor and account, and paid tiers are L3 | not pursued |

### Evidence (read-only Supabase queries, 2026-10-21)

- `pg_available_extensions`: **pg_cron 1.6.4** and **pg_net 0.20.0** are available.
- `pg_extension`: neither is enabled. **supabase_vault 0.3.1** is enabled; `vault.secrets` holds 0 rows.
- No existing heartbeat, run-log or watchdog table (`information_schema.tables` search).
- PostgreSQL 17.6. `pg_default_acl` in `public` grants **EXECUTE on new functions to anon and authenticated** by default, so the migration revokes it explicitly.

### What was built

| file | what |
|---|---|
| `research/ops/proposed_2026-10-21_t076_dead_man_observer.sql` | **Proposed, not applied.** Enables pg_cron and pg_net (guarded); creates `watchdog_heartbeats` and `watchdog_liveness_alerts` (RLS on, everything revoked from both browser roles including TRUNCATE, `service_role` may insert and read heartbeats only); `dead_man_liveness()` (the verdict) and `dead_man_liveness_alarm()` (the alarm); schedules it hourly at :17. |
| `build/check-pre-fight-coverage.js` | Every run writes a heartbeat (`ok` / `breach` / `error`) and reads the observer's latest heartbeat back. A new step-summary heading, **"Who watches the watchdog"**, says one of: not installed, never ran, stale, running but NOT ARMED, running and armed. **It never changes the exit code.** Before the migration is applied the write fails harmlessly and the summary says "NOT INSTALLED". |
| `research/ops/T076_DEAD_MAN_OBSERVER_RUNBOOK.md` | The owner's steps, the checks after, and how to undo it. |
| `tests/dead-man-observer.test.js` | 46 checks (Node, no network). |
| `tests/test_t076_observer_sql.py` | 16 tests that run the migration against a throwaway Postgres 16 cluster with `cron` / `net` / `vault` stubbed. |
| `.github/workflows/dead-man.yml`, `build/check-pipeline-health.js` | Comments only. Both still say the hole is **open** until the owner step is done. |

### The design choices that matter

- **Only scheduled runs count.** A manual `workflow_dispatch` proves the script works. It does not prove GitHub is still running the schedule, which is the thing being watched. Manual and local runs are stored but ignored by the verdict.
- **The database stamps the time, not the sender.** A trigger forces `ran_at := clock_timestamp()`. A run with `COVERAGE_NOW` set (pretend time) writes no heartbeat at all.
- **30 hours**, the same window as `watchdog-cadence.js` (`WORST_ACCEPTABLE_HOURS`) and `check-pipeline-health.js`. A test fails if the three disagree.
- **One issue per stall.** The alert row is UNIQUE on the heartbeat the stall is stuck behind, and it is inserted **before** the request is sent, the same order `user_alert_deliveries` uses. A new heartbeat starts a new episode.
- **No token, no pretending.** A stall with no token in Vault is recorded as `not_configured`, and every observer pass records `armed` so the dead man can say "NOT ARMED" on its next run.
- **Each watches the other.** If the database is down, the dead man already fails loudly in GitHub. If GitHub stops, the database notices. If pg_cron stops, the dead man's summary says the observer is stale (3-hour window). The case left uncovered is both stopping at once.

### Verified

- `python -m pytest tests/test_t076_observer_sql.py`: 16 passed against a real local Postgres 16. Two mutations were tried and each was caught: removing the EXECUTE revoke on the alarm function, and removing the UNIQUE dedupe.
- `node tests/dead-man-observer.test.js`: 46 passed. `tests/dead-man.test.js` (73) and `tests/pipeline-health.test.js` (13) are unchanged and pass.

### Not verified

- **Real pg_cron, pg_net and Vault.** These were stubbed locally. The SQL uses the documented signatures (`cron.schedule(name, schedule, command)`, `net.http_post(url, body, params, headers, timeout_milliseconds)`, `vault.decrypted_secrets`), but it has never run on Supabase.
- **PostgREST's exact error for a missing table.** The script treats `PGRST205` or `42P01` as "not installed". Any other error reads as "unreadable", which is still not reported as healthy.
- **Whether GitHub accepts the issue request.** The runbook gives the query against `net._http_response` that shows GitHub's status code.
- **The Supabase plan's own billing terms.** The extensions are bundled. If the plan bills for anything these use, this becomes L3 item 6.

### The owner's steps

1. Create a fine-grained GitHub token for `Cage-Metrics` only, with **Issues: read and write** and nothing else.
2. Apply the migration with `psql` (L3 item 5).
3. Run `select vault.create_secret('<token>', 'cfl_github_issue_token', ...)` in the SQL editor.

Then run the checks in the runbook. Until all three are done, the hole stays
open, and every dead-man run says so.

## T-081 — official fight footage links

**Verdict: retire.** Revival conditions are at the end of this section.

### Why the code is not the expensive part

Building the data file, a link list in Fight Lab's last-five list and tests
would take about a day. It would sit empty. What T-081 actually needs is
**someone to find and check links for every card, every week, indefinitely**,
and none of the following changes that:

1. **The sandbox cannot do the checking.** It has no general internet (the
   agent proxy refuses tunnels to most hosts). GitHub Actions does have internet
   access, but "hand-checked" means a person.
2. **The volume is large and keeps coming.** A typical card has about 13 fights,
   so 26 fighters, each with up to 5 past fights listed: up to ~130 candidate
   links per card. On the cards in the next 30 days there are 100 fighters
   (measured 2026-10-21). Most past fights are probably not on a free official
   upload. That could not be checked from here, but if it holds, the list will
   be patchy, and a link on one fight and none on the next reads as an
   oversight.
3. **A URL cannot show it is official.** A YouTube watch URL does not encode
   the channel, so no validator in the repo can enforce "never an unofficial
   upload". YouTube's keyless oEmbed endpoint (`/oembed?url=…` returns
   `author_url`) could confirm the channel from GitHub Actions. That makes the
   check cheaper, but finding the right video for a given fight is still a
   person's job.
4. **The task's own success test needs a migration first.** "Measure whether
   anyone clicks before widening" needs a new analytics event. Event names live
   in three places that must agree: `cfl.EVENTS`, the
   `funnel_events_known_event` CHECK constraint, and `ANALYTICS_SCHEMA.md`.
   `cfl.track` drops unknown names. So the measurement needs a production
   schema change (L3 item 5) before the first link is worth adding.
5. **"Authorised platforms" includes paid ones.** UFC Fight Pass is a
   subscription. Linking to a paywall from a research page is a commercial
   choice for the owner, not a build task.
6. **Positioning.** D-011 makes CFL a research and market-intelligence tool:
   capture schedule, provenance, consensus, movement and matchup comparisons.
   Footage links are a convenience that sits beside that, not part of it. The
   2026-10-13 HANDOFF already said T-081 should go ahead "only if it serves the
   first-ten-customers goal; otherwise it waits".

An empty scaffold would be code that has to be maintained and tested, and
re-read every time Fight Lab changes, for a feature with no owner for its data.
Retiring the task costs nothing and the reasoning above stays on record.

### Revive it if

- someone (the owner, or a named helper) commits to curating links for each
  card, **and**
- the owner approves the funnel-event migration, so clicks can actually be
  counted.

At that point the cheap design is a **static JSON file in the repo**, not a
table: one row per `fight_id`, holding the URL, the host, the channel confirmed
by oEmbed, and who checked it and when. Each link then goes in through a
reviewed pull request (which is the audit trail), and there is no RLS, grant or
migration for the data itself.

## T-082 — expanded style labels

**Verdict: retire. It conflicts with D-030.** One small fix that fits D-030
shipped with this review.

### The conflict

D-030 (owner, 2026-10-16): *"The fighting style is the UFC's listed
discipline, not a calculation."* The calculated striker / grappler / hybrid
label was removed from every page. A **calculated** line may still not claim a
background. T-082 proposes more calculated labels (boxing-led, kick-heavy,
clinch-heavy, offensive / defensive wrestling, submission threat), which would
sit beside the UFC-listed discipline and compete with it. That is exactly what
D-030 removed.

The conflict is concrete. UFC.com's own "Fighting style" field (copied into
`fighters.fighting_style`, measured 2026-10-21) has these most common values:
MMA 310, Freestyle 145, **Striker 145**, Jiu-Jitsu 58, Muay Thai 57,
Kickboxer 44, Boxing 40, **Grappler 37**, Brazilian Jiu-Jitsu 32, Boxer 25,
Wrestling 24, Karate 19. So the UFC itself uses "Striker" and "Grappler". A
calculated "kick-heavy striker" next to a UFC pill reading "Boxing" or
"Grappler" would put two sources disagreeing on one screen. That is the
Joaquin Buckley problem D-030 was written to end. Of the 100 fighters on cards
in the next 30 days, 79 have a UFC-listed style. Generic entries like "MMA"
are hidden by `disciplineRead`.

### What survives, and is already shipped

T-082's re-scope pointed out that the per-fight breakdown is already stored
(`fights.a_/b_{head,body,leg,distance,clinch,ground}_landed`). That data is
**already used**, as measured lines with the number beside them, in
`fight-overview.js::tendencies`. Each proposed sub-label already has a
numbered line covering the same ground:

| T-082 sub-label | measured line already shipped |
|---|---|
| boxing-led vs kick-heavy | `distance` (share landed at range), `legs` / `body` / `head` (share by target) |
| clinch-heavy | `clinch` (share landed in the clinch) |
| offensive wrestling | `shoots` (attempts per 15 min, with accuracy), `control` (control time per 15) |
| defensive wrestling | `tddef` / `tdweak` (stopped X of Y attempts) |
| submission threat | `subtries` (attempts per 15), `subwins` (X of Y wins by submission) |

A line with its number and sample already does what a label would do, and it
does not compete with the UFC's listing. Labels also needed a validation study
(stable from fight to fight, agreeing with a hand-labelled sample) that was
never designed. With nothing left to ship, the study has no purpose.

### Fixed in this branch (D-030-compatible)

`fight.html` still explained the **retired** calculation under the new
UFC-listed pill:

- The section subtitle said the style "is read from what they actually did in their recent fights, not from their reputation".
- The footnote said "Style compares what a fighter does in round one … 'Mixes both' means … Three labels is deliberately coarse".

Both were wrong from 2026-10-16 onwards, because the pill above them shows
UFC.com's listing. They now say where the style comes from: UFC.com, or a
correction marked "Set by CFL". They also say that what a fighter actually does
is in the measured tendencies, each with its number. The `fight-overview.js`
comments that still mentioned `styleRead` were updated to match.

New guards:

- `tests/fight-lab.test.js`: no page carries the retired calculated-style copy. The old `fight.html` matches it twice, so this test would have caught the bug.
- `tests/fight-overview.test.js`: no tendency or result line carries a style label (T-082's sub-labels, or striker / grappler / mixes both / hybrid) across four profiles that produce 9 to 11 lines each. It also checks that each sub-label's measured replacement is still in the file.
