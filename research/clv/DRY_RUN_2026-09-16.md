## Plain version

We froze the rules for measuring whether our posted prices beat the market. Then
we pointed the measuring script at the data we have.

It cannot measure anything yet. Not because the picks are bad or the maths is
wrong — because we never recorded two things the rules need: **what time each
fight was scheduled to start**, and **closing prices from three real
sportsbooks**. The prices we do have near a card come from a price-averaging
service and a prediction market, and the rules exclude both on purpose.

So the honest answer today is "we can't tell yet", and the honest fix is to
change what gets captured, not to loosen what gets measured.

## How this was produced

`settle_clv.py --clv001 --report` could not be run in the session container:
there is no `SUPABASE_SERVICE_ROLE_KEY` here, and `fight_odds` has no `SELECT`
policy for `anon`, so the publishable key returns zero rows with no error. The
counts below were derived **read-only** through the Supabase MCP connection,
reproducing the script's check order query by query. They are what
`--clv001 --report` will print once it can authenticate.

Anything read-only is safe to re-derive; anything that writes was not run at all.

## Preflight — write mode refused

false, so `--write` exits non-zero without writing a value for any row.

| condition | state | why |
|---|---|---|
| `protocol_readable` | ok | |
| `protocol_frozen` | ok | `status: frozen` |
| `protocol_version_matches` | ok | `protocol.json` 1.0.1 = `scoring.py` 1.0.1 |
| `protocol_sha256_matches` | ok | markdown hashes to the recorded `protocol_sha256` |
| `quote_provenance_present` | ok | `fight_odds.id` exists, so the consensus can reference exact rows |
| **`eligible_book_list_frozen`** | **FAIL** | see below |
| **`schema_present`** | **FAIL** | the nine CLV-001 columns are not on `model_edges`; the migration is proposed and unapplied |
| **`provider_market_ids_captured`** | **FAIL** | `fight_odds` carries no provider market id (§4 item 9) |
| **`scheduled_start_available`** | **FAIL** | *(reason corrected — see the note at the top)* `v_fight_start_best` resolves only `event_date_fallback` for every settled card. The ledger works; it has been collecting since 2026-09-14 and already has `provider_commence` for 16 future fights |

### `eligible_book_list_frozen` — **RESOLVED the same day by Amendment 2**

The gap below was real and is now closed. Ten sportsbooks are named in
`protocol.json`, taken from `v_odds_books_sportsbooks` — a view that predates
CLV-001. See Q-02 in the protocol for the list and why its provenance is what
makes it defensible.

The original finding is kept as written:

Q-02 resolved to *"fixed **NAMED** sportsbook list frozen at protocol freeze"*.
**The list was never written down.** `protocol.json` records the rule and not its
content.

The script will not derive one. A list assembled now, from whichever books happen
to be present in the data, is book selection after the fact — precisely what
DUR-001 forbids and precisely what freezing the list was meant to make
impossible. `settle_clv.py` reads `protocol.eligible_books` or refuses; there is
no fallback.

**This needs an amendment naming the books, and it should be written before
anyone looks at which books would help.** It is the one blocker on this list that
is a document defect rather than a capture defect.

## Row-level result — 47 rows, one reason

47 live edges sit on cards that have already happened, across 8 distinct event
dates. Every one fails at the same check, and it is an early one:

| reason | rows |
|---|---|
| `no_scheduled_start` | **47** |

Q-01 resolved to *"last eligible quote strictly before the **scheduled** start,
within 45 minutes"*. That needs a scheduled start **instant**. The database has
`events.event_date`, a DATE with no time, and `fights.bell_at`, which is
populated on no rows at all. There is no reference instant to measure to, so no
row reaches the book-count check.

**No substitute was invented.** Midnight on the event date, or the card's first
bout, or "some time that evening" would each produce a number, and each would be
a different definition from the frozen one, chosen after the fact by whoever
implemented it. R-04 forbids exactly that, and the protocol says so in its own
terms: a missing input leaves the row unscored, counted and reported.

### What the rows would hit next, if a scheduled start existed

Worth knowing, because it decides whether fixing `bell_at` alone would help. It
would not.

| | rows |
|---|---|
| live edges on past cards | 47 |
| with **any** two-sided sportsbook pair on file | 7 |
| with **≥3** two-sided sportsbook pairs on file | 7 |
| with ≥3 **inside the 45-minute window** — under the most generous reference instant available (end of the event day) | **0** |

The freshest two-sided sportsbook quote on any past card was captured **157.8
hours — 6.6 days — before the card**. The 45-minute limit was set from measured
near-card cadence (30-minute interval + 15-minute grace) and fixed before any
result was computed. Nothing comes close.

So with `bell_at` populated tomorrow, all 47 rows would move from
`no_scheduled_start` to `stale_close`. Still zero scored.

### Why `is_closer` is no help

`fight_odds.is_closer` is set on exactly two books, and CLV-001 excludes both:

| book | closer rows | fights | capture instants |
|---|---|---|---|
| BFO Consensus | 15,362 | 7,681 | **all `1970-01-01`** |
| Polymarket | 423 | 212 | live-era |

BFO Consensus is a feed-side aggregate — already a blend of other books' margins,
so de-vigging it is not the same operation as de-vigging a book — and every row
of it is epoch-stamped, which R-13 rejects outright. Polymarket is a prediction
market, excluded from the primary by Q-03.

The real sportsbooks — FanDuel, DraftKings, BetOnline.ag, BetRivers, Bovada,
BetUS, BetMGM — appear in `fight_odds` and are **never flagged `is_closer`**.
CLV-001 does not read the flag anyway (Q-01 selects by timestamp), but it is
worth recording that the flag and the protocol point at disjoint sets of rows.

## What this does not say

- It does not say CFL's picks beat or lose to the close. **No CLV statistic was

  rule frozen before any of this was measured, which is the only reason the
  refusals are worth anything.
- It does not move the publication gate. Storing a number is not showing one, and
  no number was stored.

**What that verification does not cover**, and must not be read as covering: that

real card yields three two-sided books inside 45 minutes of a bell. Those need
the migration applied and one card captured. The earliest that can happen is the
first card after it lands.

Until then `--clv001 --report` is the only mode that does anything, and what it
does is tell the truth about coverage. That was the point of building it before
the number existed rather than after.
